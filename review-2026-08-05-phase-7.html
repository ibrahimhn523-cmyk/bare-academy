مراجعة شاملة نهائية — Phase 7 (Polish & Deploy)

التاريخ: 2026-08-09 | المشروع: Trader Event Evaluation Platform | نوع المراجعة: تجميعية عابرة للمراحل 1-6 بالكامل (holistic) — وليست مراجعة مرحلة واحدة | المراجِع: reviewer agent (مستقل) — كتبها الجلسة الرئيسية لأن وكيل reviewer لا يملك أداة Write

القرار العام: غير آمن للاعتماد/الدفع (push) في وقت المراجعة. اكتشاف حرج جديد لم يُلتقط في أي مراجعة مرحلة سابقة: كلمة مرور admin الفعلية كانت مسرَّبة بالنص الصريح داخل pm-log.md نفسه — الملف الذي يوثّق أن كلمة المرور "حُجبت من ملفات أخرى". هذا الاكتشاف عُولج فوراً بعد المراجعة (انظر ملاحظة التحرير أدناه) — باستثنائه، بقية المحاور الأربعة المطلوبة (عزل المقيّمين، مخاطر vercel.json/sw.js، RLS) نظيفة فعلياً بالفحص المباشر.

ملاحظة تحرير لاحقة لنفس الجلسة (فوراً بعد استلام هذه المراجعة): كل قيمة سرّية وردت في هذا التقرير حُذفت واستُبدلت بوصف مكانها فقط — بما في ذلك سطر pm-log.md الذي وُصف كمصدر التسريب أدناه (كان يحتوي القيمة الحرفية في نسخة مسودة أولى من هذا التقرير نفسه، وحُذفت قبل الحفظ النهائي، تفادياً لتكرار نفس الخطأ الذي يوثّقه). تبقى نقطة C1 الثانية أدناه (فحص تاريخ git المحلي قبل push) معلَّقة — تحتاج أداة git لا أملكها في هذا الاستدعاء، مكتوبة كتوصية صريحة في §٦ من report-phase-7-polish.html.

🔴 حرج

C1 — كلمة مرور admin الفعلية كانت مسرَّبة في pm-log.md (على الأرجح مُلتزَمة بالفعل بـ git)

المكان: pm-log.md، السطر الذي يوثّق خطوة [20] من سجل Phase 1 — الجملة تصف "التحقق أن كلمة المرور حُجبت من ملفَي plan/report الخاصين بـ Phase 1"، لكن الجملة نفسها كانت تتضمّن القيمة الحرفية بدل الإشارة إليها فقط.

السبب: مفارقة توثيقية — توثيق إصلاح تسريب سابق أعاد إنتاج نفس التسريب. pm-log.md غير موجود في .gitignore (الذي يستثني فقط trader-schema.sql و*.sql)، وسطر آخر في نفس الملف يذكر أن كوميت 558613b التزم "14 ملف" — وpm-log.md غير مذكور ضمن الملفات غير المتتبَّعة (??) في git status المعطى في بداية الجلسة. دليل قوي (لا يعتمد على تنفيذ أمر git، فقط على قراءة الحالة المعطاة) أن الملف مُلتزَم حالياً بمحتواه.

الأثر: بما أن لا push حدث بعد (مؤكَّد في TRADER_NOTES.md §٦)، الوقت متاح للإصلاح قبل أي دفع لـ remote — إن دُفع كما كان، ستصبح كلمة المرور جزءاً دائماً من تاريخ Git على GitHub (يتطلب rebase/force-push للتنظيف لاحقاً، أصعب بكثير من الإصلاح الآن).

التوصية: (١) حجب القيمة في pm-log.md — ✅ نُفِّذ فوراً بعد استلام هذه المراجعة. (٢) الأهم والمتبقي: قبل أي push، افحص (عبر git log -p pm-log.md) ما إذا كانت النسخة المُلتزَمة تحتوي كلمة المرور في تاريخها، وإن كانت كذلك ففكّر في git commit --amend/rebase -i لتنظيف التاريخ المحلي طالما لم يُدفع بعد.

C2 — كلمة مرور trader admin مُعادة الاستخدام من كلمة مرور dashboard المكشوفة أصلاً في README.md

المكان: README.md (توثيق كلمة مرور dashboard القديمة) مقابل trader-schema.sql (سطر seed حساب admin يستخدم نفس القيمة الحرفية).

السبب: ملاحظة جديدة تحديداً بسياق مشروع trader، وليست تكراراً لملاحظة CLAUDE.md القديمة عن README (تلك كانت عن كلمة مرور dashboard وحدها). النقطة الجديدة: trader-schema.sql يستخدم نفس القيمة الحرفية كـ"seed password مؤقتة" لحساب admin في منصة التقييم، بينما هذه القيمة منشورة بالفعل عبر HTTP (README.md ملف عادي في جذر مستودع static site بلا build step — سيُخدَّم على /README.md تماماً مثل أي ملف HTML آخر). كل التبرير الأمني في TRADER_NOTES.md §٢ وtrader-schema.sql كان يفترض أن كلمة المرور "لن تُنشر عبر HTTP لأنها في ملف SQL مستثنى" — لكنها بالفعل منشورة عبر HTTP، من طريق آخر (README.md)، منذ ما قبل مشروع trader.

الأثر: أي شخص يملك رابط bare-academy.vercel.app/README.md (أو نسخة GitHub للمستودع لاحقاً) يعرف كلمة مرور admin الافتراضية لمنصة trader دون الحاجة لأي تسريب جديد.

التوصية: لا تكتفِ بتوصية TRADER_NOTES.md ("غيّر كلمة المرور بعد أول دخول") كخطوة مستحبة — اجعلها إلزامية قبل تسليم /trader/admin لأي طرف آخر، لأن كلمة الإقلاع ليست سرّاً فعلياً أصلاً.

⚠️ تحذير

W1 — dashboard.html.backup (ملف untracked حالياً) يحتوي أسراراً حقيقية — خطر عند أي git add . مستقبلي

المكان: dashboard.html.backup — يحتوي مفتاح API لجوجل، رابط سكربت، وكلمة سرّ سكربت من مشروع Google Sheets القديم.

خارج نطاق ملفات trader مباشرة، لكن هذا الملف untracked في نفس الجلسة التي تُبنى فيها ملفات trader — احتمال التقاطه سهواً ضمن git add . عند تنفيذ commit trader القادم. ليس تسريباً حالياً (غير مُلتزَم)، لا علاقة له بمنصة trader نفسها، فقط تنبيه سياقي.

W2 — لا rate limiting على login() في trader (امتداد متوقَّع لقرار "ج" الموافَق عليه، ليس مشكلة جديدة)

المكان: trader/lib/session.js، دالة login()

القرار موافَق عليه أصلاً (نفس تسامح portal.js الموروث) — لكن بخلاف portal.js (مستخدمون داخليون معروفون)، رابط /trader قد يُشارَك في فعالية بجمهور أوسع نسبياً (مقيّمون متعددون قد يتشاركون الرابط). فقط توثيق أن نطاق المخاطرة أعلى قليلاً من portal الأصلي.

✅ سليم (تحقّق مباشر بالكود، لا افتراضاً)

عزل المقيّمين — مطبَّق فعلياً في كل نقطة فُحصت
  • trader/views/stores-list.js — استعلام trader_evaluations مفلتر بـ evaluator_username=eq.<session.username> فقط. المقيّم لا يرى حتى عدد تقييمات غيره.
  • trader/views/rate.js — استعلام مزدوج store_id=eq.X&evaluator_username=eq.<current> — لا مسار لجلب تقييم مقيّم آخر، وزر الحذف يعمل فقط على existingEvaluation المصدره هذا الاستعلام المفلتر.
  • trader/views/admin.js — يحمّل كل التقييمات بلا فلتر، لكن هذا صحيح ومتوقَّع لدور admin (تجميع عبر كل المقيّمين). لا مكان في الواجهة يعرض هوية/درجة مقيّم فردي لمقيّم آخر أو لأي طرف — فقط متوسط مجمَّع + عدد.
  • view/board.js — إعادة تأكيد بعد Phase 6: الاستعلامات عبر sbSelectCols بأعمدة محدودة صراحة (store_id,scores فقط) — لا evaluator_username، لا created_by. session.js غير مستورَد في board.js أصلاً.
مخاطرة الانحدار على الموقع الأصلي — لا تصادم مكتشَف

vercel.json يحتوي فقط rewrites لـ /trader/:path* و/view/:path* — سلوك Vercel الافتراضي يخدم أي ملف مطابق فعلياً (dashboard.html, portal.html, index.html, leaderboard.html, tournament.html) قبل تطبيق أي rewrite؛ لا تقاطع لأنه لا ملف/مسار حالي يبدأ بـ/trader أو /view. sw.js — الـ regex الجديد الذي يستثني مسارات trader/view من cache-first غير مُثبَّت بحدود صارمة، لكن فُحصت كل أسماء الملفات الحالية ولا واحد منها يحتوي "trader"/"view" كسلسلة فرعية غير مقصودة. الأثر العملي الوحيد: ملفات review-*.html الجديدة (تحتوي "view" كسلسلة فرعية) تُستثنى أيضاً من cache-first — غير ضار (صفحات توثيق تُخدَّم من الشبكة).

RLS في trader-schema.sql — كما هو موثَّق تماماً، لا فجوة إضافية

الجداول الأربعة كلها: ENABLE ROW LEVEL SECURITY قبل إنشاء السياسات — الترتيب صحيح، لا جدول منسي بلا تفعيل رغم الادّعاء. السياسات الأربع FOR ALL USING (true) WITH CHECK (true) — permissive بالكامل كما هو موثَّق ومقبول (القرار ج)، متسقة بين الجداول.

السياق العربي — سليم فيما فُحص

logical properties في كل مكان تقريباً (استثناء موثَّق لـ.trader-toast)، تحويل أرقام عربية-هندية شامل في ar.js (باستثناء موثَّق لكلمة المرور المولَّدة لسبب وظيفي)، لا نصوص إنجليزية ظاهرة للمستخدم.

ملخص الإجراء المطلوب قبل أي push

  1. حجب كلمة المرور الحرفية في pm-log.md — تم.
  2. التحقق مما إذا كانت الكوميتات المحلية الحالية تحتوي القيمة القديمة في تاريخها، والتفكير في تنظيف التاريخ (rebase/amend) طالما لا push حتى الآن — معلَّق، يحتاج git.
  3. اعتبار كلمة مرور trader admin الافتراضية غير سرية فعلياً (منشورة أصلاً عبر README.md) — تغييرها إلزامي وليس مستحباً فقط قبل تسليم /trader/admin لأي طرف ثالث — معلَّق، بيد إبراهيم بعد أول دخول.
  4. الانتباه عند git add القادم لعدم التقاط dashboard.html.backup — تنبيه فقط.

لا مشاكل أخرى حرجة في المحاور الأربعة المطلوبة (تسريب الأسرار، عزل المقيّمين، مخاطر الانحدار، RLS). عزل المقيّمين، RLS، وتوافق vercel.json/sw.js مع الموقع الحالي — كلها سليمة بالفحص المباشر.
