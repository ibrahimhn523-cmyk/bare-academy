١. سياق التنفيذ — كيف بدأت هذه المرحلة

بعد كتابة plan-phase-1-foundation.html وعرض القرارات الخمسة (أ-د + سؤال Service Worker)، وصلتني رسالة من الجلسة المنسّقة تنقل أنك وافقت حرفياً بعبارة "موافق نفذ" على الخطة كاملة بدون تعديلات. بناءً عليها بدأت التنفيذ الفعلي أدناه.

ملاحظة شفافية مهمة (رفعها أيضاً وكيل المراجعة المستقل بشكل مستقل عني): قسم "📝 ملاحظات الراعي" في plan-phase-1-foundation.html ما زال فارغاً — لا يوجد سطر مكتوب منك بخط يدك في الملف نفسه، فقط رسالة منقولة عبر الجلسة المنسِّقة. القرار (ج) تحديداً (كلمات مرور نصية + RLS مفتوحة) كانت الخطة تنص أنه "يحتاج تأكيدك الصريح تحديداً — لا موافقة عامة". نفّذت بناءً على الرسالة المنقولة لأن الفعل الأخطر فعلياً (تشغيل SQL على قاعدة بيانات حية) ما زال بانتظارك يدوياً في Supabase Studio — أي يوجد بوابة أمان أخيرة قبل أي أثر حقيقي على البيانات. لكن أنصح أن تكتب سطراً واحداً في قسم ملاحظات الراعي بـ plan-phase-1-foundation.html يؤكد نفس الموافقة كتابةً، ليبقى السجل التوثيقي متسقاً مع بقية عمليات هذا المشروع.

٤. النتائج الحرجة من المراجعة — وكيف عُولجت

🔴 C1 — لا موافقة مكتوبة من الراعي في ملف الخطة نفسه

الحالة: لم تُعالَج تلقائياً — تحتاج فعلك. شرحتها بالتفصيل في القسم ١ أعلاه. التوصية: اكتب سطراً في "📝 ملاحظات الراعي" بـ plan-phase-1-foundation.html يؤكد موافقتك، خصوصاً على القرار (ج).

🔴 C2 (الأخطر تقنياً) — trader-schema.sql كان سيُنشر كملف عام عبر HTTP فور أول push

الحالة: عُولجت. لأن bare-academy موقع static بدون build step ولا استثناءات نشر، أي ملف في جذر المستودع مُلتزَم بـ git يصبح قابلاً للتنزيل المباشر بعد النشر (مثل bare-academy.vercel.app/trader-schema.sql) — وهذا كان سيفضح كلمة مرور admin / [محجوبة — انظر trader-schema.sql محلياً] علناً لأي زائر، وليس فقط "مدفونة في تاريخ Git" كما ظننت أولاً. الإصلاح: أنشأتُ .gitignore (أول ملف من نوعه في المستودع) يستثني trader-schema.sql بالكامل من التتبّع — يبقى الملف على قرصك محلياً لتنسخ منه SQL يدوياً في Supabase Studio، لكنه لن يُضاف لأي commit ولن يُنشر مع الموقع أبداً. هذا يطابق فعلياً نمط ADR-008/ADR-012 الموثّق أصلاً في CLAUDE.md: "DDL يدوي خارج الريبو".

🔴 C3 — تعليق "من فحص security-check" داخل السكربت لم يكن موثّقاً في pm-log.md وقت المراجعة

الحالة: عُولجت. الاستدعاء كان حقيقياً (عبر أداة Skill الفعلية، لا نصاً مُحاكى)، لكنه لم يكن مسجَّلاً بعد في pm-log.md لحظة قراءة reviewer للملف — فجوة توقيت في التوثيق لا تزوير. أضفت السجل الكامل لخطوة security-check في pm-log.md (الوقت، المُدخل، الناتج) ليطابق قاعدة "اكتب لحظة التنفيذ".

٥. ملاحظات ⚠️ من المراجعة — غير حرجة، مسجَّلة كمتابعة لاحقة (لم تُغيَّر بها الـ schema)

الـ schema المُنفَّذة تطابق حرفياً Section G المعتمدة من التعليمات (تأكيد reviewer صراحة: "لا انحراف بنيوي"). النقاط التالية أُبقيت كما هي في هذه المرحلة عمداً (تعديلها الآن كان سيعني تغيير schema معتمدة بدون رجوع لك عبر decision-guard من جديد) — وثّقتها هنا لتُعالَج في Phase 4 إن رغبت:

  • حذف مستخدم مرتبط ببيانات: trader_stores.created_by وtrader_evaluations.evaluator_username بلا ON DELETE صريح — حذف مقيّم أضاف متجراً أو قيّم سيفشل بخطأ قيد مفتاح أجنبي. الحل المقترح لاحقاً: تعطيل (is_active=false) بدل حذف فعلي، أو ON DELETE RESTRICT مع رسالة عربية واضحة في واجهة Phase 4.
  • لا قيد DB على بنية عمود scores: عمود JSONB بلا CHECK يربط القيم بحدود max_score لكل معيار — مع RLS المفتوحة، القيم قابلة للتلاعب مباشرة عبر REST متجاوزة تحقق الواجهة. مقبول لسياق فعالية داخلية، لكن يستحق تنويهاً دائماً.
  • تأكيد مشروع Supabase: لم يصلني تأكيد صريح أن oytfhgqhibbcsqbnvwyv هو المشروع الصحيح لتشغيل هذا الـ SQL عليه.
  • اختبار preview فعلي لـ vercel.json: لم يحدث بعد (لا تشغيل فعلي متاح لي) — تقييم نظري فقط أن لا تعارض مع الملفات الثابتة الحالية. يُنصَح باختباره على رابط معاينة قبل أي push لـ main.
  • دقة regex استثناء sw.js: مبني على مطابقة جزئية للنص (substring) بدل حدود مسار صارمة — غير ضار حالياً (فحصتُ كل الملفات الفعلية) لكنه هش لأسماء ملفات مستقبلية تحتوي "trader" أو "view" كجزء من الاسم.

٦. ما لم أستطع تنفيذه — يحتاج فعلاً منك أو من الجلسة المنسِّقة

لا أملك أداة تنفيذ أوامر (Bash/shell) في هذا الاستدعاء — فقط أدوات قراءة/كتابة ملفات ومهارات ووكلاء. لذلك لم يحدث أي مما يلي، ويحتاج تنفيذاً يدوياً:
  1. تشغيل SQL: افتح trader-schema.sql (بجذر المستودع محلياً على جهازك) وألصق محتواه في Supabase Studio → SQL Editor ونفّذه يدوياً. تحقق بعدها: select * from trader_users; وselect * from trader_criteria;.
  2. git commit محلي: نفّذ الأوامر التالية بنفسك (أو عبر الجلسة المنسِّقة إن كان لديها صلاحية Bash): 
    git status
git add vercel.json sw.js .gitignore plan-phase-1-foundation.html report-phase-1-foundation.html review-2026-08-05-phase-1.html pm-log.md
git commit -m "feat(trader): add DB schema and routing rewrites"
    لاحظ: trader-schema.sql عمداً غير مُضاف للقائمة (مستثنى الآن عبر .gitignore، والسبب موثّق في القسم ٤ — لا يُلتزَم به لأنه يحتوي كلمة مرور نصية وسيُنشر عبر HTTP). تأكد أن git status يُظهر فقط هذه الملفات ولا يضيف dashboard.html.backup أو index.html.bak أو bareeq-tournaments-exploration.md أو .claude/ (غير متعلقة بهذه المرحلة).
  3. لا push بعد — هذا كان commit محلي فقط حسب التعليمات، والدفع لـ main ينتظر اختبار preview لـ vercel.json.
