خلاصة صادقة بجملة واحدة: الكود كامل ومكتوب لكل المراحل السبع، مراجَع بعمق (سطراً بسطر في نقاط الأمان الحرجة)، وتم اكتشاف وإصلاح تسريب فعلي لكلمة مرور admin في ملفَي مراجعة + في هذا السجل نفسه. لكن لا شيء اختُبِر حياً بعد — trader-schema.sql لم يُنفَّذ أبداً على Supabase الحقيقية، فلا يوجد جدول trader_users ولا trader_criteria على القاعدة الحية حتى الآن. كل بند في هذا التقرير يميّز بوضوح بين "الكود صحيح بالمراجعة" و"عمل فعلياً أمام إبراهيم".

١. الاكتشاف الحرج في هذه المرحلة — وكيف عُولج

🔴 تسريب فعلي لكلمة مرور admin — 3 مواضع، اثنان مُلتزَمان بالفعل محلياً بـ git

عند فحص شامل (Grep على كامل شجرة المشروع) اكتُشف أن كلمة مرور admin الافتراضية كانت موجودة بالنص الصريح في:

  1. review-2026-08-05-phase-1.html — في نصّي نتيجتين "🔴 حرج" (المفارقة: المراجعة التي حذّرت من التسريب كانت هي نفسها التسريب).
  2. review-2026-08-05-phase-3.html — في بند "💡 تحسين" يقتبس نص Section K.1 المرجعي.
  3. pm-log.md — السطر [20]، وهو بالمفارقة نفس السطر الذي يوثّق "التأكد أن كلمة المرور حُجبت من الملفات الأخرى".

الثلاثة ملفات git-tracked وغير محمية بـ .gitignore (الذي يستثني فقط trader-schema.sql و*.sql). pm-log.md على الأرجح مُلتزَم فعلاً بمحتواه القديم ضمن الكومتات المحلية الخمس السابقة (لا أداة Bash لدي للتأكد بـgit log -p — يحتاج فحصاً يدوياً، انظر §٦).

✅ المعالجة

استُبدلت القيمة الحرفية بـ [محجوبة] في الملفات الثلاثة، مع إضافة ملاحظة تحرير صريحة في كل ملف توضّح أن المعنى/القرار التاريخي لم يتغيّر — فقط حُذفت القيمة السرية. هذا لا يكفي وحده: إن كانت النسخة القديمة (بالقيمة المكشوفة) موجودة في تاريخ الكومتات المحلية الحالية، تعديل الملف الآن لا يمحوها من التاريخ. التوصية الموثَّقة في §٦ أدناه: فحص git log -p pm-log.md قبل أي push، والتفكير في تنظيف التاريخ (rebase/amend) طالما لم يحدث push بعد — هذه آخر فرصة سهلة.

⚠️ اكتشاف إضافي (C2 من مراجعة reviewer الشاملة): كلمة مرور trader admin الافتراضية أصلاً ليست سرّاً

القيمة المُستخدَمة كـ seed password لحساب admin في trader-schema.sql هي نفسها كلمة مرور dashboard.html القديمة، الموثَّقة والمنشورة أصلاً في README.md — وbare-academy موقع static بلا build step، فـREADME.md يُخدَّم علناً عبر HTTP تماماً مثل أي صفحة HTML أخرى فور النشر. أي شخص يعرف رابط bare-academy.vercel.app/README.md يعرف كلمة مرور admin الافتراضية لمنصة trader، بغض النظر عن أي حجب لاحق في ملفات المراجعة.

لم أعدّل README.md — خارج نطاق تكليف Phase 7 صراحةً (يخص مشروعاً/قراراً مختلفاً: تدوير كلمة مرور dashboard نفسها)، وهو قرار أوسع يحتاج موافقتك المباشرة. التوصية المسجَّلة في TRADER_NOTES.md §٢ ("يُنصَح بتغيير كلمة المرور فور أول دخول") يجب اعتبارها إلزامية لا اختيارية — القيمة الافتراضية غير سرية فعلياً من اليوم الأول.

٢. ما تحقّق فعلياً في Phase 7 (بلا تعديل جديد مطلوب)

  • sw.js: تأكيد قراءة مباشرة أن استثناء /trader و/view من cache-first (السطر 42، regex /(?:dashboard|portal|trader|view)/) لا يزال صحيحاً وفعّالاً — نفس الإصلاح المُنجَز في Phase 1، لا حاجة لتكراره.
  • vercel.json: يحتوي فقط rewrites لـ /trader/:path* و/view/:path*. لم يُلمَس، ولم يُنشأ ملف جديد. مراجعة reviewer الشاملة أكّدت أن Vercel يخدم أي ملف مطابق فعلياً (index/dashboard/portal/leaderboard/tournament) قبل تطبيق أي rewrite — لا تصادم مع الموقع الحالي.
  • لا لمس لـ index.html / dashboard.html / portal.html: مؤكَّد — لم يُقرأ أي منها للتعديل في هذه المرحلة.
  • لا vercel.json جديد: مؤكَّد — الملف الموجود من Phase 1 لم يُعدَّل.

٣. مراجعة reviewer الشاملة النهائية (holistic)

استُدعي وكيل reviewer لمراجعة عابرة للمراحل 1-6 مجتمعة (لا مرحلة Phase 7 فقط)، بأربعة محاور إلزامية: تسريب الأسرار عبر كل الشجرة، عزل المقيّمين الفعلي، مخاطرة الانحدار على الموقع الأصلي، وRLS الفعلية. التقرير الكامل في review-2026-08-05-phase-7.html. ملخص النتائج:

  • 🔴 تسريب كلمة المرور (معالَج في §١ أعلاه).
  • 🔴 إعادة استخدام كلمة مرور مكشوفة أصلاً في README.md (موثَّق في §١ أعلاه، يحتاج فعلك).
  • ⚠️ dashboard.html.backup (ملف untracked من مشروع منفصل تماماً — Google Sheets القديم) يحتوي أسراراً حقيقية (API key، سكربت باسورد) — لا علاقة بـtrader، لكن تنبيه سياقي لتفادي التقاطه سهواً بـgit add . عند تنفيذ commit trader القادم.
  • ✅ عزل المقيّمين: تحقّق سطراً بسطر في stores-list.js، rate.js، admin.js، view/board.js — لا تسريب هوية/تقييم فردي لمقيّم آخر أو للعامة في أي مكان.
  • ✅ RLS: الجداول الأربعة كلها ENABLE ROW LEVEL SECURITY قبل السياسات، permissive بالكامل كما هو موثَّق ومقبول (القرار ج) — لا جدول منسي.
  • ✅ لا تصادم مسارات بين vercel.json/sw.js الجديدين وأي ملف من الموقع الحالي.

٦. ما تبقى — يدوياً بيدك أو بيد الجلسة المنسِّقة (بالترتيب)

  1. حرج/عاجل: افحص git log -p pm-log.md (أو أي أداة git) لمعرفة إن كانت النسخة القديمة المسرَّبة موجودة في تاريخ الكومتات المحلية الخمس الحالية. إن كانت كذلك، فكّر في تنظيف التاريخ (git rebase -i أو commit --amend للكوميت المعني) قبل أي push — بعد push يصبح التنظيف أصعب بكثير (يتطلب force-push وتنسيقاً مع أي متعاون آخر، وليس لديك أي حتى الآن حسب معلوماتي).
  2. تشغيل trader-schema.sql يدوياً في Supabase Studio → SQL Editor (الملف محلي على جهازك، مستثنى من git عمداً).
  3. تغيير كلمة مرور admin فور أول تسجيل دخول ناجح — أصبح إلزامياً بعد اكتشاف C2 (القيمة الافتراضية منشورة أصلاً في README.md لمشروع مختلف).
  4. اختبار محلي أو Preview Deployment فعلي (vercel dev أو رابط معاينة) لتغطية كل بنود N.2-N.8 الموسومة ⏳ أعلاه — لا بديل عن اختبارك اليدوي لأن لا أداة تشغيل خادم/متصفح متاحة لهذه الجلسة.
  5. موافقتك الصريحة على push لـ main — لم يحدث أي push حتى الآن، طوال المشروع بالكامل من Phase 1 إلى Phase 7.
  6. اختياري: عند تنفيذ git add القادم، انتبه لعدم التقاط dashboard.html.backup سهواً (يحتوي أسراراً من مشروع Google Sheets القديم غير المتعلق بـtrader — لاحظه reviewer كتنبيه سياقي فقط).
